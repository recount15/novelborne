# 06 更改提交规范

## 1. 改动前（必做）

1. **先侦察后动手**：grep 全部引用点（代码、测试、构建脚本、spec、文档），一处不漏；结构整理期翻车的根因全是"漏了某种引用形式"（缩进 import、`as` 别名 import、字符串 mock 目标、`parents[N]` 深度）。
2. **大改动先备份**：跨目录移动/批量改写前，把涉及目录复制到临时位置（如 `/tmp/fe_backup/`）。
3. **评估爆炸半径**：改公共模块（distill/persistence/catalog/fate_engine）前，先跑相关测试套件确认基线是绿的。

## 2. 改动中

- **小步验证**：每完成一个可独立验证的阶段就跑一次相关测试，不攒到最后。
- **批量改写用脚本不用手**：正则批量替换后必须 grep 复查变体形式（行首/缩进/`as` 别名/字符串字面量/注释示例）。
- **路径与结构改动同步更新**：代码、测试、构建脚本（build/*.bat、build/*.spec）、.gitignore、README、standards/——六处视为一个事务。
- **不动不该动的**：任务范围外的文件不"顺手优化"；发现预存问题先记录再单独处理（避免与本次改动混在一起无法归因）。

## 3. 改动后（完成定义）

1. 全量回归绿：`python -m unittest discover -s tests -t .`。
2. 冒烟验证：改后端就起服务打 `/api/health` + 相关端点；改前端就 `npm run build` 过类型检查。
3. 文档同步：用户可见行为变化 → 更新 README.md；结构/约定变化 → 更新 standards/；新增历史设计文档 → docs/ 且头部加「⚠️ 历史文档」标注。
4. 服务进程：改了运行时代码必须提醒重启服务（旧进程不会自动加载新代码——本项目已发生两次"修了但旧进程还在跑"的乌龙）。

## 4. 提交信息（若使用 git）

- 中文、祈使句、一句话说清"改了什么+为什么"：`修复锚点蒸馏首章失败后不重试的永久卡死`。
- 一次提交一个主题；重构与功能修改分开。
- 提交前确认 `.gitignore` 生效：var/、frontend/dist、__pycache__ 不入库。

## 5. 禁止事项

- 禁止跳过测试直接交付（"回头再补测试"等于没修）。
- 禁止在未备份的情况下做跨目录批量移动。
- 禁止静默删除文件——删除必须 grep 引用并更新全部引用点。
- 禁止把"删不掉"（环境安全策略拦截）的残留隐瞒不报——必须明确列入交付说明。
