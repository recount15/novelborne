# 状态记忆系统规范

## 目标

状态面板记录每回合已经确认的世界事实，供不同模型继续生成时使用。模型可以提出状态变更，但不能直接把自然语言正文当作状态事实写入。

## 固定字段

状态快照必须使用 `fate-engine-state` schema，包含：

- `world`：世界名称、规则和当前世界条件
- `time`：日期、时刻、时区、天序、昼夜
- `location`：地点、区域、空间关系
- `body`：身体状态、伤势、异常、疲劳、精神状态
- `assets`：货币、装备、物品、债务、收入
- `abilities`：技能、修为、金手指状态、冷却和代价
- `relationships`：人物关系、信任、阵营态度
- `goals`：当前目标、任务、伏笔、承诺
- `knowledge`：已知、未知、误判和信息来源
- `scene`：章节、回合、场景、锚点和待处理事项
- `flags`：最后更新时间、动态世界书命中和冲突

章节与回合统一放在 `scene.chapter` 与 `scene.round`，不单列 `chapter` 分类。提交未声明的分类会被程序拒绝。

## 每回合协议

分两次提交，把「玩家想做什么」和「世界实际发生了什么」分开：

1. 玩家提交行动时，只把行动登记到 `scene.pending`，不预设任何结果。
2. 模型生成回复后，程序从回复中抽取有明确文本依据的变化（时间、地点、伤势、物品、能力、认知）。
3. 程序校验分类、类型、来源和数值范围；校验失败保留上一版快照。
4. 通过校验的变化提交为新快照，并清空 `scene.pending`。
5. 追加 `history` 版本记录，保留前后差异。
6. 本回合命中的世界书条目写入 `flags.last_worldbook`。
7. 生成叙事和状态面板。正文与面板不混写。

因此「玩家宣称做到」不等于「状态已改变」：行动失败时状态不会被写入既成事实。

## 跨天续读

日期变化必须由已确认的时间推进或原文依据支持。程序识别「次日 / 第二天 / 翌日」推进一天，「第三天 / 两天后 / 后天」推进两天，并记录昼夜时段；显式日期与时刻（`1999年3月5日`、`14:30`）直接采用。天序保存在 `time.day_index`，面板显示为「第 N 天」。

跨天时保留未完成任务、伤势、冷却、关系和物品，不得因为重新加载模型而重置。读档后先恢复快照，再恢复世界书冷却和章节回合。

## 面板输出格式（所有模型统一）

状态面板由程序渲染，模型不需要也不允许自行拼装。任何模型接入后，只需遵守两条：叙事里写清可验证的时间、地点、伤势、得失与认知变化；不要声称面板内容。程序据此渲染固定十行：

```
### 状态记忆面板
- **时空**：<地点> ｜ <日期> <时刻> <时段> ｜ 第 N 天
- **身体**：<状态>；伤势 <列表>；异常 <列表>；疲劳 <数值>
- **资产**：货币 <列表>；装备 <列表>；物品 <列表>
- **能力**：技能 <列表>；修为 <文本>；金手指 <名称/状态/冷却/代价>
- **关系/阵营**：<人物> ；<阵营>
- **目标/伏笔**：目标 <列表>；任务 <列表>；伏笔 <列表>
- **认知**：已知 <列表>；未知 <列表>；误判 <列表>
- **进度**：第 X 章，第 Y 回合；场景 <名称>；锚点 <列表>
- **待结算**：<本回合已提交但未落地的行动>
- **世界书命中**：<条目 ID> ｜ 待澄清 <冲突>
```

## 冲突处理

无法确认的事实写入 `knowledge.unknown` 或 `knowledge.misconceptions`，不得写入 `world`、`body`、`assets` 等当前事实字段。冲突写入 `flags.conflicts`，等待原文、玩家确认或后续事件解决。
