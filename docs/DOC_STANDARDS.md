# 文档规范（DOC_STANDARDS）

> 原则：**文档跟着代码走**——改了行为必须同步文档；文档与代码冲突时，
> 以代码为准并立即修文档。禁止"设计宣称"式写作（写的是希望的行为），
> 只写实测行为。

## 1. 文档地图（单一职责，不重复）

| 文档 | 回答的问题 | 何时更新 |
|---|---|---|
| `README.md` | 这是什么、怎么跑起来 | 功能面变化时 |
| `docs/ARCHITECTURE.md` | 代码怎么组织、数据怎么流 | **每次重构提交的同一 commit 内** |
| `docs/HANDBOOK.md` | 接手者怎么活下来（环境/测试/发布/已知问题） | 流程或已知问题变化时 |
| `docs/DOC_STANDARDS.md` | 文档本身怎么写（本文） | 规范变化时 |
| `standards/*.md` | AI 协作宪法（架构/代码/数据/接口/测试/提交/文件 七维规范） | 工程纪律变化时 |
| 代码 docstring | 这个函数做什么 | 改函数时（同 commit） |

不设其它文档：历史设计稿一律不入库（测绘/设计等过程产物在 `var/refactor/`，
git 忽略）。

## 2. 写作规则

- **架构文档**：模块表必须含"实际职责"（一句话，以代码为准）与依赖方向；
  数据流图必须能对应到函数名
- **手册**：命令可直接复制执行；已知问题必须带复现条件与规避方式
- **commit message**：中文，首行 ≤50 字概述，正文列要点（改了什么、为什么、
  验证方式）；重构提交注明 Phase 与闸门结果
- **行号引用**：文档里禁止写死行号（易腐），写函数名/搜索锚点
- **密钥与版权**：任何文档不得含 API Key、IP 资产路径、内部备份位置

## 3. 评审清单（文档变更过审三问）

1. 文中行为描述是否逐条在代码里核实过？
2. 是否有另一份文档已在讲同一件事（重复即删除或合并）？
3. 接手者按本文操作，是否每一步都能成功？
